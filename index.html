Approve from wherever you are

“I want my agent to keep working when I step away, but it stalls on the first approval prompt.”

Most of what an agent does is safe. The trouble is the few calls that aren't, and a prompt on a laptop you just walked away from.

  • The request comes to your phone. Approve or deny with a tap in Telegram, or open the approval page and confirm with your passkey.
  • Safe calls never wait. Rules per tool and per argument decide what's allowed, what asks you and what's denied. Reading an issue goes through; posting a comment asks.
  • Answer once, not every time. “Allow always” and “Deny always” remember a decision for the exact call, one repository or the tool, within limits the gateway checks.
  • Or install the approval app. Its push notifications say what's being asked. Deny right on the notification; Approve opens the request for your passkey, or answers in one tap on devices you allow. You can answer “always” from the app too, and it keeps your approval history.

See what you're approving

“Honestly, I click yes without really reading what it's asking.”

A tool name and a blob of JSON don't tell you much. So people stop reading, and an approval prompt turns into a habit.

  • Previews of the real thing. The file change as a diff, the email as it will be sent, the full text of a comment and the issue it goes on.
  • Built by the gateway, not the agent. Previews come from the checked arguments and read-only lookups the gateway makes itself, so the agent can't dress up what you see.
  • The agent's own words are fenced off. An agent can explain why it wants something. That text is shown separately and labelled as written by the agent.
  • No preview, no pretending. If a preview can't be built, the page says so and shows the raw arguments. It never approves on its own.

Rules the agent can't get around

“I set up careful auto-approve rules. The agent still found a way around them.”

Rules inside the agent are suggestions to a program that can rewrite its own setup, call a different tool or simply log itself in somewhere else.

  • The agent never holds the credential. Tokens for GitHub, Google and Home Assistant stay with the gateway, under a different user. The agent only gets a gateway token.
  • A floor no agent can lower. Deny and ask rules in the policy floor beat every agent file, shared rule set and remembered “Allow always”.
  • It can't hand itself more access. Adding collaborators, creating deploy keys, setting Actions secrets and changing branch protection are denied in the shipped GitHub rules.

One agent, blocked on GitHub, tried to log itself in to GitHub with full repo access. Behind AgentPass there's no token on the agent's side to find, and the things that would give it lasting access are denied by default.

Nothing on the agent's side to leak

“My agent did something serious I never meant it to, and a secret got out.”

When the agent holds the keys, one bad instruction or prompt injection can use them in ways you never intended.

  • No secrets to exfiltrate. The agent can read everything it has and still not find a service token.
  • Risky actions need a person. Sending mail or changing a file asks you first, the most sensitive calls can require your passkey, and deleting a repository is denied outright.
  • Every call is on the record. The audit log keeps who asked, what was called, what was decided and by whom, and the agent can't edit it.

Example: GitHub with you in the loop

Your agent triages issues and drafts replies. Nothing reaches GitHub until you've seen it.

  1. The agent drafts a reply to an issue and asks AgentPass to post it.

  2. Your phone shows the full comment and the issue it goes on, in the right repo.

  3. You read it, then approve or deny.

  4. The gateway posts it with its own token. The call is in the audit log.

Private repos, without a token on the agent

To pull a private repo, the agent asks to update a read-only mirror to one exact commit. You see the repo, branch, commit and its headline before you approve. The gateway fetches it, and the agent pulls from the mirror with plain git. For your own repos you can allow this always, per repository.

Merges need your passkey

When the agent asks to merge a pull request, you see the branches, the size of the change and the commit you’re approving, with a warning if GitHub reports conflicts. Every merge needs your passkey, and GitHub refuses it if new commits arrived after you approved.

How it works

AgentPass sits between your agent and the services it uses. The agent asks; the gateway decides, asks you when needed, and makes the call.

  • The agent connects over a local Unix socket, a WebSocket, or MCP, with its own token. Each agent gets its own rules and its own audit trail.
  • The gateway decides. Deny beats allow, allow beats ask. When a call needs you, it builds the preview and sends the request to every approval channel you've set up.
  • The first valid answer wins. Then the gateway makes the call with its own credentials and returns only the result to the agent.

What's in the box

Policy per tool and per argument

Allow, ask or deny by pattern on the call itself, such as gh_put_contents(*, main).

A policy floor

Deny and ask rules no agent file, shared rule set or remembered decision can relax.

Approval channels

Telegram buttons and a passkey approval page. A rule can require a passkey for the calls that matter most.

Passkeys

WebAuthn on your phone or laptop. Only public keys are stored on the gateway.

Trusted previews

Diffs, rendered email, comment text, device state, Home Assistant automations and what a delete removes, built by the gateway.

Remembered decisions

“Allow always” and “Deny always”, per exact call, per repository or per tool, with limits on what can be remembered.

Audit log and dashboard

Every call, decision and resolver, browsable on an admin-only dashboard.

Agents connect their way

Unix socket, WebSocket or MCP, a CLI and a Python SDK. One token and one rule set per agent.

Any HTTP API in YAML

Tools are declared in YAML: arguments, validation, request and preview. GitHub, Gmail, Calendar, Drive and Home Assistant ship ready to use.

Offline config check

agentpass check-config catches broken rules, missing previews and unsafe settings before you start.

Approval app with push notifications

Install the approval page as an app. Deny from the notification, Approve in one tap on devices you allow, answer “always”, and keep your history at hand.

Git mirror

Pull private repos from a read-only mirror, updated to one approved commit at a time, with no token on the agent.

The security model, plainly

AgentPass assumes your agent can run any command as its own user, including a prompt-injected one. It assumes the agent can't become root or read another user's private files.

✓What it protects against

  • The agent reading service tokens, OAuth tokens or the bot token.
  • The agent approving its own request, through any channel it can reach.
  • The agent changing its own permissions or another agent's.
  • The approval showing something other than what will run: previews come from the gateway.
  • Silent actions and a tampered audit log.

✕What it doesn't

  • Someone with root on the gateway machine.
  • A compromised phone or passkey of the person approving.
  • A service that is itself malicious or compromised.
  • You approving something harmful after reading it.
  • Misuse that stays inside a rule you set to allow.

The full threat model is in docs/DESIGN.md.

Get started

Run the gateway on a Linux machine you trust, such as a home server, a NAS or a VPS, as its own user. Your agent runs as a different user on the same machine.

  1. Prepare the machine

    As root: a service user for the gateway, a group for the agents allowed to connect, and a directory for the socket. Replace your-agent-user with the user your agent runs as.

    useradd --system --create-home --home-dir /var/lib/agentpass --shell /usr/sbin/nologin agentpass
chmod 700 /var/lib/agentpass
groupadd agentpass-clients
usermod -aG agentpass-clients agentpass
usermod -aG agentpass-clients your-agent-user
install -d -o agentpass -g agentpass -m 0755 /run/agentpass

    /run is emptied on reboot; a systemd unit with RuntimeDirectory=agentpass recreates it. The design doc has the full layout and service hardening.

  2. Install

    As the service user, so the agent can't read anything you put here:

    sudo -u agentpass -H bash
cd ~ && git clone https://github.com/Anima-t3d/agentpass && cd agentpass
python3 -m venv .venv && . .venv/bin/activate
pip install .

    On the agent's side you only need the client:

    pip install "git+https://github.com/Anima-t3d/agentpass"

  3. Configure

    Put AGENT_TOKEN, GUARDIAN_BOT_TOKEN and GITHUB_TOKEN in .env (chmod 600 .env), then write config.yaml:

    gateway: {}

listen:
  socket: /run/agentpass/agent.sock
  group: agentpass-clients

agent:
  token: "${AGENT_TOKEN}"

messenger:
  type: telegram
  telegram:
    token: "${GUARDIAN_BOT_TOKEN}"
    chat_id: -100123456789     # your Telegram chat
    allowed_users: [123456789] # who may approve

services:
  github:
    url: "https://api.github.com"
    auth: { type: bearer, token: "${GITHUB_TOKEN}" }
    tools: "tools/github.yaml"

storage:
  type: sqlite
  path: "./data/agentpass.db"

    And permissions.yaml: reads go through, everything else asks, and nothing that deletes or hands out access ever runs.

    defaults:
  - pattern: "gh_get_*"
    action: allow
  - pattern: "gh_list_*"
    action: allow
  - pattern: "*"
    action: ask

rules:
  - pattern: "gh_delete_*"
    action: deny
  - pattern: "gh_add_collaborator*"
    action: deny
  - pattern: "gh_*_deploy_key*"
    action: deny
  - pattern: "gh_set_actions_secret*"
    action: deny
  - pattern: "gh_update_branch_protection*"
    action: deny

  4. Check and start

    set -a; . ./.env; set +a
agentpass check-config --config config.yaml
agentpass serve --config config.yaml --permissions permissions.yaml

    Then, as the agent's user:

    agentpass tools --socket /run/agentpass/agent.sock --token "$AGENT_TOKEN"

Is AgentPass for you?

✓A good fit if

  • Your agent uses real accounts: GitHub, email, calendar, the smart home.
  • You want it to work while you're away, and still decide on the risky calls.
  • You run a machine you trust: a home server, a NAS, a VPS.
  • You're comfortable editing YAML and running a small Python service.

✕Probably not if

  • Your agent has no real credentials, so there's nothing to protect.
  • It runs in a throwaway sandbox you'd happily wipe.
  • You want zero approvals, ever. AgentPass can allow a lot, but its point is asking about the rest.
  • You have no machine you trust to hold the keys. A hosted option may come later, see below.

Open source, always

AgentPass is MIT licensed and self-hosted. Your credentials and your audit log stay on your machine. No account, no telemetry.

Don't run a server?

A hosted version may come later, for people who'd rather not run their own. AgentPass itself stays open source either way.

Questions

Does it work with my agent?

If your agent can run a command, speak MCP, or open a WebSocket, yes. There's a CLI, a Python SDK, an MCP endpoint and a ready-made skill for OpenClaw.

Where do my credentials live?

On the gateway, readable only by the gateway's own user. The agent gets a gateway token that can ask for tool calls and nothing else.

What happens when I'm away or don't answer?

The request waits for an answer, 15 minutes by default. If nobody answers, the call isn't made and the agent is told it timed out. Calls your rules allow keep working, and remembered decisions answer repeat requests for you.

Can the agent change its own rules?

No. Rules live in files the agent can't write, and anything that would hand out access, like adding a collaborator or a deploy key, is denied by the shipped GitHub rules.

Which services are supported?

GitHub, Gmail, Google Calendar, Google Drive and Home Assistant ship as YAML tool files. Any other HTTP API can be added in YAML, and a Python plugin covers the rest.

What does it cost?

Nothing. It's MIT licensed and runs on your own hardware.
